# Operations dashboard, 2026-10-19

Synthetic workload on the available 12-logical-CPU Linux host with `GOMAXPROCS=4`: 1,000,000 spans across 20,000 runs. This is not an independent 4-vCPU/8-GB machine. Data was seeded with `scripts/benchmark.go -stream-spans 50 -target-spans 1000000`; the 50-span paced segment is too short to assess sustained ingest.

`scripts/benchmark_query.go` measures warm, serial database calls. The operations window includes all generated runs in the last 24 hours, including 980,000 unpriced LLM spans. It includes no recorded bodies, scores, simultaneous ingestion, HTTP serialization, or browser rendering.

| Measurement | Result |
| --- | ---: |
| Operations p95 before optimization, 10 samples | 2,162 ms |
| Operations p95 after partial unpriced-span index, 10 samples | 1,489 ms |
| Operations p95 after reading run metadata once and aggregating exact percentiles in Go, 10 samples | 249 ms |
| List 50 runs across offsets 0–19,950, 100 samples | p95 3.93 ms |
| Open one 50-span run, 100 samples | p95 0.56 ms |

With ten samples the nearest-rank p95 is the largest measurement; these results establish a local baseline, not a production latency guarantee. Percentiles retain three `int64` durations per completed run, so memory grows with the selected run count. Quality aggregation with a large score history still needs its own workload measurement.
